# 文档写作规范

让每份文档可被搜索、对新人可读、对维护者精确。核心方法只有两条：**每个事实只有一个家**，以及**每条可机械检查的规则都配一个可执行的检查**。其余规则都是这两条原则的展开。

## 一、写作前的决策顺序

动笔之前按此顺序决定，不要边写边想：

1. **定位**：这份文档挂在文档树的哪个位置？位置决定它的详略权限——只详细描述自己的主题，对下级主题只说目的和职责，细节链接到归属它的文档。
2. **定型**：判定为教程（tutorial）或参考（reference）。教程按步骤走向一个结果，只引入每步所需的概念；参考定义查找范围和当前行为，不安排教学顺序。两者内容都很多时必须拆开。
3. **定读者**：写教程前，先私下判定读者的起点知识和每个概念的难度（初/中/高级），前置知识先于依赖它的概念出现，过难的材料移到后续教程或参考。
4. **下沉细节**：把属于下级的解释替换为指向归属文档的链接。

## 二、分层：每个事实只有一个家

同一事实只允许存在一个归属处；其他地方需要它时，写一行链接，不复述。判断"该写在哪"用下表：

| 层级 | 职责 | 不放什么 |
|---|---|---|
| 根 AGENTS.md | 常驻指令：agent 每次会话都必须记住的规则，每条 1–3 行，附链接到其归属文档 | 故事、完整示例、从链接文档复述的内容 |
| 子目录 AGENTS.md | 该子树特有的指令 | 根文件已覆盖的全仓规则 |
| 架构文档 | 有序地图：组成、核心模块、扩展点 | 类型定义（→ 模块参考）、决策理由（→ 决策记录） |
| 模块/包 README | 该模块的契约：配置、语义、限制、扩展点 | 注释复述、生成目录复述、其他模块的事 |
| 决策记录（ADR 等） | 为什么这么定、放弃了什么、如何验证；已落地的用现在时描述现实 | 迁移计划、验收清单、"应该……"式规格语言 |
| 事后复盘（postmortem） | 事故故事——唯一允许叙事体的层级 | — |
| 操作手册（cookbook） | 带编号验证步骤的 how-to | 设计理由（→ 决策记录） |
| 生成的目录/索引 | 由源码或生成器产出 | 任何手改 |

放置速查：bug → 复盘；理由 → 决策记录；步骤 → 手册；类型定义 → 模块参考；包契约 → README；常驻规则 → 根 AGENTS.md。

## 三、命名与放置：固定家，可搜索的名

每类文档的目录与命名模式全项目只定一次，写进 `doc-structure.json`（见第九节），由门禁执行；之后任何文档不落第二处、不起第二种名。

| 文档类型 | 文件名模式 | 为什么 |
|---|---|---|
| 决策记录 | `yyyy-mm-dd-主题.md`，日期是首次提出日 | 同类决策按时间自然排序；定稿后改内容不改日期，入站链接不腐 |
| 事后复盘 | `NNNN-主题.md`，单调递增编号 | 复盘靠编号互相引用，编号发出即不复用 |
| 操作手册 | 动宾短语，命中"怎么做 X" | 读者带着任务来，文件名就是检索词 |
| 常驻文档 | 全项目唯一（一份架构文档、一套 README 序列） | 同名第二份必然漂移 |
| 生成的目录/索引 | 归生成器命名 | 手改即腐烂（第二节） |

主题段用短横线连词或中文，写读者会搜索的词，不写内部代号。目录里的 README.md、AGENTS.md 是导航与指令，不受类型模式约束。不建集中索引页：目录树就是清单，手抄索引必然与树漂移。

## 四、标题与章节骨架

- **每份文档恰好一个 H1**，是 frontmatter 之后的第一行内容，点明主题；标题用读者会搜索的词。
- **开头一段写"它能做什么"**：读者能用这份文档达成什么、何时该读它；不写它的角色与类型——身份由路径和骨架自己说。
- **同类文档同一副骨架**，读者才能靠位置找信息：

| 文档类型 | 必备章节（按序） |
|---|---|
| 决策记录 | 问题 → 决策 → 备选方案 → 后果 |
| 事后复盘 | 影响 → 时间线 → 根因 → 修复 → 预防 |
| 操作手册 | 目标 → 前置条件 → 编号步骤，每步带验证 |

"备选方案"是决策记录的必填章：每个被否决的方案及落败原因各一段。不记录被击败的备选，决策就会被反复重提——这正是决策记录要防止的失败。项目扩展骨架时写进 manifest，不在个别文档里碰运气。

## 五、写作规则

- **只写当前状态，不写变更史。** 持久文档中禁止"之前/现在/不再/已改名/已移动"和 PR、提交号；点名活着的机制本身。变更故事属于提交信息、决策记录或复盘。
- **一段一个物理行**，靠编辑器软换行。代码块、表格、列表保持原格式。
- **文档中的代码必须真实可运行。** `check_docs.py` 会实际编译/解析 fenced 代码块（见第九节）；贴类型声明时确保与源码同步，更好做法是引用源码位置而非粘贴。
- **注释与文档字符串写完整契约，不写推理过程。** 保留行为、失败、时序、所有权、异常与后果；删除叙述、测试走读、评审记录、代码复述。契约留在本地，理由链接出去。
- **直接表达：点名行为者和事实。** 不用隐喻。写"响应字段""JSON 校验""ESM 导出"，不写"响应的形状""校验边界"。`contract/契约` 只用于前置条件、后置条件、不变式、兼容性承诺这类调用方与实现方共同依赖的义务。
- **链接用相对路径**，不用裸文件名；指向标题的锚点必须真实存在。

## 六、事实核查：跑了再写

文档描述的是产品今天的行为。对操作性声明（命令、默认值、报错、平台差异），唯一可接受的证据是**亲手执行过**：

1. 逐条运行文档将要展示的命令、配置片段、示例，只写观察到的结果，包括确切的输出、警告和失败模式。
2. 复现不了的内容直接删掉。绝不凭记忆、类比或邻项目的 README 搬运命令、字段、默认值。声明无法复现时，改声明，不改测试。
3. 修改既有文档前，先对照当前最新代码核实相关段落——旧文档里过时的陈述依然是错的，按代码改正，不按旧散文改。

## 七、反 slop 清单

写完任何文档后逐条自查：

- 同一规则出现在多个地方 → grep 一个有辨识度的短语，只留一个家，其余改链接。
- 历史叙述："之前""现在""不再""曾经""已改名"、PR 号、提交号 → 只写当前事实。
- 实现状态标注（"已实现！""未来：……"）→ 状态会腐烂，由代码和目录结构自己说话。
- 手写的目录、清单、状态盘点 → 有源码或生成器作为权威来源时，删除手抄版。
- 推理转录：逐步实现叙述、显然分支的证明、测试走读、被否决的备选方案 → 只留最终契约或持久的理由。
- 兄弟条目各自重复同一段理由 → 理由上移到拥有它的能力或公共说明处，写一次。
- 段落墙：一段里塞多条规则和括号插叙 → 拆开或把细节降级到其归属处。
- 强调通胀：到处是加粗、全大写、"严重注意" → 强调只留给真正改变行为的那一句。

## 八、长度自律与预算

为每个常驻文档设定上限，写进项目根目录的 `doc-budgets.json`，由 `check_docs.py` 强制执行（逐文件上限优先于 `--max-lines` 全局默认值；manifest 里列了但文件不存在也算违规）：

```json
{
  "budgets": {
    "AGENTS.md": { "max_lines": 150 },
    "docs/architecture.md": { "max_lines": 300, "max_chars": 20000 }
  }
}
```

中文文档没有可靠的"词数"，用行数（结构复杂度）和字符数（信息密度）两个维度即可。超标时按此顺序处理：

1. **迁移**：把属于其他层级的内容搬走，留一行链接。
2. **压缩**：属于本文档但能更短的内容写短。
3. **提额**：仅当内容确实需要空间时提高上限，并在变更中说明理由。

上限是护栏不是削减目标：达标后保留至少 5% 余量；超标期间冻结上限直到回落。删除散文若会改变承诺的行为而不仅是解释，先提出行为变更，而不是偷改文档。

## 九、机器门禁

规则不靠自觉。每条可机械检查的规则都应有一个可执行的检查，并在提交前运行。本 skill 附带 `scripts/check_docs.py`，可移植到任意项目：

```bash
python3 <skill目录>/scripts/check_docs.py <文档目录或文件>...
```

检查项：

- 一段一行违规、历史叙述禁用词、相对链接与锚点有效性；
- 逐文件长度预算（`doc-budgets.json`，见第八节；未列入的文件用 `--max-lines`，默认 800 行）；
- 每文件恰好一个 H1，且是 frontmatter 之后的第一行内容；
- 命名与骨架（`doc-structure.json`）：按目录声明文件名正则与必备 H2 章节（按序）。决策记录目录拒收无日期前缀的文件，缺"备选方案"章的记录判违规；manifest 里列了但目录不存在同样算违规；同目录的 README.md、AGENTS.md 豁免。同目录混居多个文档家族时，目录值用 `{"rules": [...]}` 为每家各定模式与骨架，文件须命中至少一条规则；规则内的 `exclude` 按文件名或相对目录路径豁免特殊文件在该目录的全部结构检查。
- **代码块真实编译**：` ```python `/` ```json `/` ```bash ` 内建支持；` ```js ` 需要环境里有 node；` ```ts ` 需要项目本地或 PATH 中的 tsc——文档里的代码必须真的能编译，这是"只写当前状态"的机械保证。ts 块仅因缺少模块导入（TS2307）失败时记为跳过而非违规；用 `--no-code` 可整项关闭。

`doc-structure.json` 示例（放项目根目录自动发现，或用 `--structure-manifest` 指定）：

```json
{
  "structure": {
    "docs/decisions": { "filename": "^\\d{4}-\\d{2}-\\d{2}-.+\\.md$", "sections": ["问题", "决策", "备选方案", "后果"] },
    "docs/postmortem": { "filename": "^\\d{4}-.+\\.md$" }
  }
}
```

同目录混居多个文档家族时用 `rules` 形式，`exclude` 豁免特殊文件：

```json
{
  "structure": {
    "docs": { "rules": [
      { "filename": "^ADR-.+\\.md$", "sections": ["问题", "决策", "备选方案", "后果"], "exclude": ["ADR-legacy-multi.md"] },
      { "filename": "^PLAN-.+\\.md$" }
    ] }
  }
}
```

写文档代码块时的纪律随之升级：块要么自包含可编译，要么引用源码位置而不是粘贴。项目 CI 里跑此脚本时，应保证所用工具链（node/tsc）可用，否则对应语言的检查静默跳过。

项目成熟后应把这些检查挂进 CI 或 pre-push 钩子；新增规则时优先问"这条规则能否机械检查"，能就先写检查。

## 十、完成标准

一次文档改动算完成，当且仅当：

- 每个新事实有且只有一个家，其他地方是链接；
- 所有操作性声明都实际执行过；
- 反 slop 清单逐项自查通过；
- `check_docs.py` 与项目自有门禁全绿；
- 改动涉及的 README 和代码注释契约随代码同步更新。
